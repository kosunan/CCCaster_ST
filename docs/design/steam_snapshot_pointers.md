# Steam object poolの子ポインター3段

2026-09-11。第7担当の追加解析。対象は既知Steam EXE（SHA256 `11270cf2da851054aa6c1bff309d50b042429abd936dca5df833bcd1de5e6c46`）のディスク逆アセンブル。実機書込み・ゲーム操作・ビルドはしていない。

## 結論

1000件×stride33Cのobjectから辿る旧表の3段 `+320 → +38 → +0 → +0` は、Steamにも対応する構造がある。ただし資源の解放と再ロードを跨ぐ寿命保証は未確認なので、実稼働の子ノード表にはまだ追加しない。

`SteamSnapshotPointers.hpp` に3000子ノードの候補生成と、実稼働追加用の `AppendVerifiedNodes` を用意した。`StructureVerified=true / LifetimeVerified=false` として後者はfalseを返し、入力vectorを変更しない。呼出元はfalseを無視してスナップショット完成と扱ってはいけない。

## ポインターとデータの区別

object pool nodeをO、`F=*(O+320+index*33C)` とすると保存対象は次の3箇所。

|node|保存先|4Bの意味|
|---|---|---|
|第1子|F+38|0x1C補助構造Aへのポインター|
|第2子|A|ASV0構造Vへのポインター|
|第3子|V|ASV0データ先頭4B。ポインターではない|

実ゲーム内部はobject+4をthisとして扱うため、命令中のthis+31Cがpool起点からの+320に対応する。`0x47237E→0x472384`、`0x4A79A7→0x4A79AD` などでthis+31CからFを読み、F+38を読む。

`PointerSnapshot` は親nodeの保存先からポインターを読み、その指す先にoffsetを足して子の保存先を決める。第3子の4Bを更にポインターとして辿ってはいけない。

## 確保・書込み

通常の資源構築は `0x431317` で0x54を確保し、`0x43132F` から `0x433450` を呼ぶ。同関数は `0x43345D` で0x1Cを確保、ゼロ初期化後 `0x433496` でF+38へ格納する。

別の連続領域経路では `0x431E57→0x431E62` が資源所有者+3Cの配列先頭へ1C刻みのoffsetを足してAを選び、`0x431E77` で解析後 `0x431E7C` でF+38へ設定する。同じ構造でもallocation所有権は経路で違う。

補助構造のparser `0x4304E0` は `ASV0` タグ（little endian `0x30565341`）を `0x43055C` で判定し、`0x430563` でAの先頭がNULLなら0x0Aを確保する。`0x43057F` がA先頭へそのポインターを格納する。`0x43058C` はV+0の1B、`0x430595/0x4305A0/0x4305AB/0x4305B4` はV+2/+4/+6/+8の各2Bへ読み込んだ値を書く。

旧版は `0x408C22` が同じASV0タグ判定、`0x408C29→0x408C44` が同じ0x0A確保・先頭pointer設定、`0x408C4F/0x408C56/0x408C5F/0x408C68/0x408C71` が同じフィールド書込み。第2・第3段が旧版と同じ構造である根拠になる。タグ名だけから特定キャラクターの専用処理とは判断しない。

## 解放と寿命

`0x433570` はframe資源の解放処理。EDX=1（連続領域を外側で所有する経路）と、それ以外で処理を分ける。

- EDX!=1の経路では `0x4336C6` でF+38からAを読み、`0x4336CD` でA先頭のVを読む。`0x4336D4` でVをfreeし、`0x4336DC` でA先頭を0にする。`0x4336F9→0x4336FA` でA自身をfreeし、`0x433716` でF+38を0にする。
- EDX=1の経路は個別freeをせず `0x433603` から共通末尾へ進む。外側の資源所有者が連続領域を管理する。
- `0x433950` は所有者+34のframe集合を走査し、この解放を各frameへ呼ぶ。`0x4339AA` では所有者+30の所有モードをEDXへ渡す。
- `0x433AB0` は集合破棄から呼び、frame表側のallocationも解放する。資源置換中の `0x4326B4`、不要資源破棄の `0x43270A`、表全体の破棄の `0x433C96` からも到達する。

動作中のobjectは毎回allocationを所有するのではなく、資源表のframeを参照する。`0x4B6BF7→0x4B6C19` はframe集合の連続/ポインター配列を選び、その要素アドレスをthis+31Cへ格納する。このため同じframeを複数objectが共有し得る。

## 残る確認

資源の破棄経路が存在するため、過去snapshotの親ポインターを戻してもfree済み領域は復活しない。PointerSnapshotはNULLだけを特別扱いし、allocation世代や参照可能性を検査していない。ロード/キャラ変更/資源差替えが確実にrollback履歴破棄の外側であるか、全呼出し元とゲームスレッド境界の追加追跡が必要。

今回、通常更新中に必ずこの領域がfreeされるという証拠は得ていない。一方、複数キャラクター・変身・召喚を含め、寿命問題がないという静的証明にも達していない。構造一致を寿命保証へ読み替えない。実機の複数キャラ検証も未実施。

## 同一InGame世代への絞り込み

親担当から、SceneRunnerがフェーズ/ラウンド境界でsnapshot履歴をResetし旧世代をdrainすることを確認した。必要条件は全キャラ資源の永久保持ではなく、その同一InGame世代の保存窓内で解放/再ロードしないことである。以下の追跡はこの条件で評価した。

資源全体の破棄 `0x433C50` の直接callは `0x46F116, 0x46F17E, 0x49F96B, 0x4DFEAB, 0x4E3F83, 0x4E3FE3`。

- 最初の2箇所は `0x46F0E0` のプレイヤー4体と追加資源の一括破棄。`0x48B6F5` からの呼出しはpendingmodeを参照するモード終了処理。`0x494866→0x494873` はpendingmodeが1または5なら資源破棄を明示的にスキップする。
- `0x49F96B` は `0x49F920` の名前付き資源再ロード入口。同関数への直接callは `0x46EC07,0x486AB0,0x49FBA4,0x4E3B2A`。`0x49FBA4` 直前ではファイル名を文字列書式化している。
- `0x4DFEAB` は `0x4DFE80` の資源所有者破棄。`0x4E4263/0x4E426B` で別管理objectの+48/+54の資源に使われる。これらが戦闘objectの参照する資源と共有する条件は未確定。

召喚/生成入口 `0x4AB760` は固定1000件poolを走査して空slotを選び、`0x4AB7C0` で初期化 `0x4AB2E0` を呼ぶ。`0x4AB7C8` でpool要素+4をthisへ渡すことも確認できる。この生成入口自体はheap確保やframe資源freeをしない。frame選択 `0x4B6C19` は資源集合からの参照設定であり、召喚objectごとにASV0構造を作り直す処理ではない。

一括破棄 `0x46F0E0` への全直接callは `0x43F671,0x474EC6,0x4751D0,0x485611,0x486624,0x48B6F5,0x490D31,0x49189B,0x491BD0,0x491C40,0x491CC1,0x494873`。全入口の状態振分け、および間接呼出しを経由した再ロードの到達性までは追跡完了していない。通常の生成と資源破棄を区別できたことは前進だが、この未解決分のままLifetimeVerifiedをtrueにはしない。
