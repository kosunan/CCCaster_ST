# Steam版保存範囲の照合（第3担当、2026-09-11）

静的解析を実施。ゲーム起動・終了・プロセスメモリへの書込みは行っていない。完全な保存表、実機保存復元、Steam対戦同期はいずれも未達。`SteamSnapshotLayout.hpp` は確認済み部分範囲の RVA 記録であり、ランタイムへ接続していない。`SteamSnapshotLayoutComplete=false` を維持する。

## 対象・根拠

対象EXEとSHA256は [先行解析](2026-09-11_steam_port.md) の2版。現行 `GameSnapshotLayout.hpp` の3061ノードを機械抽出し、`RealGameMemory.cpp` の追加6領域と照合した。既存表は61ルートと、オブジェクト1000件の各3ノード、合計1,241,047B。追加6領域は19B。そのほかReplayCursorsが別保存される。

根拠は `build_logs/steam_analysis/legacy.asm`、`steam.asm`。全67項目の自動候補と命令例を `snapshot_candidates.json`、旧参照と近傍対応を `snapshot_xrefs.txt` に記録した。正規化候補は誤対応を含む。例えば旧0x557DACの候補0x5BB16Cは別関数であり不採用。Steam0x4A179Cがプレイヤー番号で0x5BEFFCを参照することを採用根拠とした。

## 保存構造の差

- プレイヤー配列: 旧0x555130→Steam0x5BC370。0xAFC×4=11248B。0x472EBF/0x472F2Bの走査・選択が根拠。ユーザー表の0x5BC378は配列先頭ではない。
- オブジェクト配列: 旧0x67BDE8→Steam0x6E28F0、0x33C×1000=0xCA260=828000B。0x4AB732〜0x4AB752で先頭・stride・終端0x7ACB50を確認。0x47DC91〜0x47DC9Dで全長ゼロクリアを確認。
- 別配列: 旧0x61E170→Steam0x684CE0、0x5DC00=384000B。0x47DCA2〜0x47DCAEの全長ゼロクリアが根拠。
- 更新状態配列: 旧0x558608→Steam0x5BF860、0x30C×5=3900B。旧0x41CA82の基点0x558908とSteam0x473736の0x5BFB60、0x473790〜0x4737C8の2つの64 DWORDクリアと5件のstrideを照合。先頭を単純な一定deltaで推測したものではない。
- カメラ: 旧0x555124の8B→0x5BC35C、旧0x5585E8の12B→0x5BF830、旧0x55DEC4の12B→0x5C9C84、旧0x564B14の12B→0x5CB63C。初期化旧0x44AFD0対Steam0x4A1500を照合。
- **分散**: カメラ倍率の旧0x54EB70/74/78はSteam0x5B3B94/0x5B3A28/0x5B3B90。旧12Bを1個のSteam区間にできない。旧0x564B0C/10もSteam0x5CB638/0x5CB648へ分散する。
- **順序逆転**: 旧残時間0x562A3C/実時計0x562A40はSteam0x5C9C58/0x5C9C54。8B一括ならSteam先頭は0x5C9C54だが、版間の同じバイト順という前提を持たない。
- RNG: 0x479990〜0x4799DAでindex 1〜55を0x5CB2BC + index×4から参照。0x5CB2C0から220Bが状態。旧表の224Bに含まれる末尾4Bの用途を未照合のまま保存範囲へ含めない。乱数値/呼出数0x5CA9BC/0x5CA9C0とindex0x5CB2B8は別。

## ポインター子・副作用

旧node36の子は1000組、各組は `*(root+0x320+i*0x33C)+0x38` の4B→その4Bのポインター先4B→さらにその先4B。親の復元後にポインターを読み直す `PointerSnapshot` 仕様を維持する。rootへだけロードベースを加算し、実ポインターには加算しない。

Steam0x474E68はobject+4をECXへ渡し、0x4A9AE8はthis+0x31Cを参照する。したがってroot上の+0x320は一致。0x47237E/0x472384等で続く+0x38を確認。ただし以降の二重ポインター先の書込み・解放寿命、全キャラでのnull条件までは未証明。後続2段を「同じに見える」という理由だけで移植してはならない。

`PointerSnapshot` 自体はポインターの読み書き可能性を検証せずmemcpyする。誤った子ノードはアクセス違反や資源破壊へ直結する。親を戻した結果が既に解放されたヒープ領域を指す場合も保存表だけでは解決しない。

現行 `RealGameMemory` は通常の表に加えReplayRound(0x140)/inputs(+0x120)→4 ReplayContainer(0x20)/ReplayState(8B)のカーソルを保存する。再確保前のstatesポインターを戻さず、現在のstates上へindex/total/total2/endOffset/最終要素を復元する。Steamのこれら構造とendptrは今回未照合。リプレイ保存無効でも内部蓄積の副作用を確認する必要がある。音声オブジェクトやOS資源の丸ごと保存を追加して代用しない。

## 続行条件

1. 未解決ルートと、部分照合の残りバイトを別々に追う。旧の隣接変数順をSteamへ転用しない。
2. オブジェクト子の第2/第3段とReplayCursorsの構造を確認する。
3. ゲームスレッド上の保存→同一入力再計算→状態一致、生成/消滅を跨ぐオブジェクト、KOスロー、再戦、キャラ選択境界を限定試験する。
4. 不完全表でSupportsSnapshots=trueにしない。完全表の構築が失敗した場合は予測を拒否する。

ヘッダー内の証拠RVAは `ImageBase=0x400000` を引いた命令位置。ASLRは維持。動作試験・ビルドは親担当へ引き継ぐ。

第4担当の独立照合を反映: 旧0x67BD78はSteam0x684CB4。0x4ADBBDで上限0x1F4、0x47DCB3でゼロ初期化。旧オブジェクト近傍へ一定deltaで移すと別用途になる。第4担当から旧0x559580→0x5C07D8、0x74D99C→0x7B450Cも報告されているが、当ヘッダーへの採用は個別の命令根拠を参照して後続で行う。
