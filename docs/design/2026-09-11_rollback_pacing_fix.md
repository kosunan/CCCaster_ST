# R4上限到達時の不要な全入力待機を修正

## 原因と処理時間

D2＋R4は60Hzで100ms分。ただしR4は未来入力を先に知る待機時間ではなく、未確定状態から戻せる最大4Fである。到着した訂正を処理する時間、採取・通信の位相差、5%損失時の次パケット到着も必要であり、片道96msが100ms以内という条件だけで全表示間隔16.667ms以内にはならない。

今回の主因は実装の待機条件だった。R4を使い切ると `SceneRunner` は未確定4件だけでなく現在フレームの入力まで全件そろうのを待っていた。最古の1件が確定すれば1枠空くのに、この余分な待機で停止と高速追いつきを繰り返していた。

修正前の通常更新＋描画（WORK）中央値は両窓約0.44ms、最大約2.5ms。再計算中央値約3.3/3.8ms、最大約5.8/6.4msに対し、入力待ちの記録は最大58.6/70.7ms。大きな表示停止の主因は処理負荷ではなく、この待機だった。

## 修正

`PredictionHistory::ReadyToResume` で、予測可能な戦闘中は最古の未確定入力が到着した時点で待機を終了する。その後にReconcileし、不一致なら保存状態へ復元して再計算する。一致なら空いた枠を使用して前進する。待機判定自体は確定位置を動かさず、不一致を取り落とさない。

R4上限、D2、60Hz絶対締切、世代境界は維持する。予測禁止の場面やR0では必要な全確定入力を待つ。通常フレームも再計算もゲームスレッド上で実行する。

## 比較実測

両試験とも45秒、自動入力、D2/R4、片道60〜96ms・損失5%。WASAPIとPACE/FRAME_TIMINGの診断を有効にした。異なる乱数の遅延・損失であり、同じパケット列の再生ではない。戦闘のplay=1開始から120Fを除き、ログに存在する実提示要求間隔を集計。平均FPSや設定値を瞬間値の代わりには使わない。

修正後のWORK中央値0.428/0.427ms、最大2.451/2.388ms。再計算中央値3.123/4.001ms、最大6.285/8.518ms。処理を含めても全フレーム16.667ms以内という達成には至っていない。残る厳しい条件では、D3/R4（計116.667ms、Dは1F増加）等で余裕を増やす選択肢がある。今回ユーザー設定は変更していない。
